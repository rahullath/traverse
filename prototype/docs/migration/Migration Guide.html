00 · Premise

You have a prototype (traverse.html) that nails the new sensibility — paper-and-ink, marginalia, no streak fire, no glowing cyan, voice that names time physics instead of the person. The repo at feature/mirror-recovery-v2 is still wearing messy-theme.css: OLED black, neon gradients, --messy-streak-fire animations. That gap is large but mechanical. The risk is not the visual swap — it's everything underneath.

Three concrete failure modes will sink this if you don't plan around them. They map exactly to what you flagged.

1. Static beauty, broken wiring. The redesign looks finished on paper but the Mirror screen renders — for runway because the new component doesn't subscribe to the same data shape. Mitigation: ship one screen at a time as a vertical slice — real Supabase data, real API calls — before generalizing.
2. Confusing navigation, especially onboarding & account. You have 20+ routes today: /dashboard, /daily-plan, /habits, /calendar, /profile, /billing, /import, /about, two onboarding bypass routes, monitoring pages, etc. Half of them implement an ethos you no longer believe in. Mitigation: collapse to seven, redirect the rest, put account management in one place — Settings.
3. Stateless ambition vs Supabase reality. "Stateless" is the goal, but the app still needs an account so NHS-bound users can sign in on another device. Mitigation: a state tier classification — every table answers "what breaks if this is forgotten?" Anything with a "nothing" answer gets deleted or auto-expired. Today's plan is the only thing that persists beyond settings, and even that expires nightly.

01 · Rollout shape

The call I'm making for you: token-first, then primitives, then a single vertical slice on Today, then IA collapse, then the rest, then deletions. A feature flag (src/lib/feature-flags.ts already exists) gates the new path until it's solid.

Why this and not the alternatives

ShapeWhy it's wrong for you, this week, solo
Big-bang. One branch, swap everything.You have a 52KB MirrorUI.tsx and a 35KB ChainView.tsx. Touching both at once in one PR means Friday is a debugger marathon, not a merge.
Token-first only. Change CSS variables, let everything inherit.Cosmetic. The whole point is that the marginalia layout (rules instead of cards, margin-marks instead of filled chips) is structural — not a recolor.
Component-by-component, leaf to root.Leaves the app bilingual for weeks — half marginalia, half cyber. Cognitive load you can't afford solo.
Screen-by-screen, behind a flag.This is what we're picking — but bias toward one screen done fully, then the rest faster once primitives are settled.
Parallel /v2 directory.Doubles your component count and you stop merging routes back. Skip.

02 · Phase 0 — branch hygiene

The boring step that prevents Friday-night chaos. Do it Monday morning, all of it, before you write a line of new code.

Kill-switch audit

List, in docs/migration/kill-list.md, every module whose presence in the new design is genuinely up for debate. Initial list — adjust as you go:

  • Habits / streaks. Stance: delete UI, archive data, drop tables. Keep src/lib/import/enhanced-loop-habits-v2.ts as a one-shot export to CSV so users can leave with their history.
  • Billing / tokens. Stance: stub getBillingSnapshot() to always return { isAccessAllowed: true }. Drop tables after a soak.
  • Dashboard. Stance: redirect to /today. There is no separate "dashboard" in a one-day-at-a-time tool.
  • Confetti / chart.js / recharts / canvas-confetti. Stance: remove from package.json at the end of the week.
  • Monitoring routes. Stance: NODE_ENV=development only.

Solo-dev safety rails

  • Run npm run build at the end of every phase. Solo means no PR reviewer; the build is your reviewer.
  • Commit on every working state, even ugly. Small reversible steps beat big "ship it" commits.
  • Keep the dev server open on a second monitor / phone, refreshing as you go.
  • Don't delete anything in this phase. Renaming and stubbing only.

07 · Phase 5 — state, retention, account

This is the part you flagged hardest. The doctrine: state earns its place by surviving the question "what breaks if this is forgotten?" Most of your current schema doesn't survive that question.

Five-tier classification, applied to your tables

Tier 1 · Identity

Persisted, unavoidable

auth.users, profiles. Email, password/oauth, display name, timezone. Nothing else.

Retention: until the user clicks Delete account. Then actually delete, don't soft-flag.

Tier 2 · Preferences

Persisted, user-tunable, bounded

user_preferences. Wake/sleep window, energy default, voice register, theme, motion, density, anchorless default, keystone visibility, time format.

These are settings, not history. They have a fixed schema and don't grow. Safe to keep.

Tier 3 · Plumbing

Persisted; required for the app to be useful

calendar_sources (OAuth tokens + sync cursor), location_travel_profiles ("Uni = 20min by tube"), manual_anchors (recurring), calendar_events (cache).

The reusable "I go to uni at this time on Tuesdays" data. Without it the chain generator can't do its job. Keep, but make it deletable from /settings/data.

Retention: calendar_events rows older than 30 days get deleted (they're a cache). Run as a daily Supabase function or a Vercel cron.

Tier 4 · Today's plan

Persisted, but auto-expires

daily_plans, time_blocks, exit_times.

The plan persists so a refresh doesn't lose it and so a phone-handoff works. But the plan is for today. Add a nightly job: DELETE FROM daily_plans WHERE date < current_date - interval '1 day'. Cascades to time_blocks and exit_times if FKs are set up — verify.

Why one day of grace? So "yesterday's plan, for reference" survives the user opening the app at 02:00 on a heavy night.

Test this. Add src/test/integration/state-retention.test.ts that seeds plans dated 3 days ago, runs the cron handler, asserts they're gone. Without a test the rule is decorative.

Tier 5 · Delete

Not consistent with the ethos

  • Habits, streaks. habits, habit_entries, src/lib/habits/*, src/components/habits/*, src/pages/habits.astro, src/pages/habits/*, src/pages/api/habits/*.
  • Billing / tokens. user_tokens, token_transactions, src/lib/billing/*, src/lib/tokens/*, src/pages/billing.astro.
  • Telemetry beyond felt-helpful. Felt-helpful is the only signal aligned with the ethos ("did the tool carry the load?"); the rest of src/pages/api/analytics/* and src/pages/api/monitoring/* should go.

Two-step deletion: (1) stop writing this week, hide the UI, stub the reads to return empty. (2) drop tables in a Supabase migration after two clean weeks. Don't drop tables the same day you stop writing them — too easy to lose data you'll wish you had to debug a regression.

Account-management UI

One place: /settings/account. You flagged this specifically. Put exactly these actions, in this order, and nothing else:

  • Email — change (re-verify), or just show
  • Password — change
  • Sign out
  • Export my data — JSON dump of preferences + last plan + manual anchors + travel profiles. One button, one file. (Plus a legacy "export habits" if the tables haven't been dropped yet.)
  • Reset today's plan — wipes daily_plans for today only; you'll be re-prompted to generate one
  • Delete account — confirms, actually deletes the row in auth.users and CASCADEs to everything. No "deactivation" middle state.

The implementation of Delete account is the one that actually has to be right. Write the endpoint, run it against your own dev account, confirm the rows are gone. If the schema doesn't cascade cleanly, fix that first — half-deleted users are exactly the "stateless ambition meets Supabase reality" failure you flagged.

  • Tier classification committed to docs/migration/state-tiers.md
  • Nightly cleanup function written + tested
  • Delete-account endpoint written + tested against your dev account
  • getBillingSnapshot() stubbed to { isAccessAllowed: true }
  • Habit write paths short-circuit; reads return []

08 · Phase 6 — onboarding rewrite

Current onboarding is twelve fields on a dark gradient page (src/pages/onboarding.astro) — exactly the optimization-theatre register you're rejecting. Replace it with the three-card flow from the prototype, plus one optional fourth card.

The four cards

  1. What does a good day start with for you?
    Choices: A place to be · A person · A meal · The light coming up
    Captures: seeds the implicit zeitgeber and the default keystone type. Stored as user_preferences.first_anchor_kind.
  2. When are you usually awake?
    Two times, defaults 07:00 and 23:00. Replaces the four wake/sleep window fields.
    Captures: wake_window_start, sleep_window_end. The other two get sensible defaults (wake_end = wake_start + 2h, sleep_start = sleep_end − 2h).
  3. When plans go sideways, what do you want?
    Choices: Alternatives, calmly · Just permission to stop
    Captures: infeasible_response + initial value for the anchor-less tweak. The "permission to stop" answer maps to anchorless: 'refuse'.
  4. (Optional) Add one place you go often.
    Label + travel minutes. Skippable.
    Captures: one row in location_travel_profiles.

Last card is content, not a form: "The goal is for you not to need this app." No CTA — just a "Begin" button that drops them at /today in the empty state.

Backend

Keep /api/auth/complete-signup.ts as-is on the API contract. Just call it with fewer fields. The defaults that plan-builder.ts needs (commitments, starting_difficulty, structure_style, min_sleep_hours) go server-side. The user can change any of them later in Settings — the onboarding is not the only door.

  • Old onboarding.astro renamed to onboarding.legacy.astro first, not deleted, in case the new flow misses a required field for downstream code
  • New flow uses <Page> + <Display> + <Button> primitives, not its own styles
  • Server defaults documented in src/lib/onboarding/defaults.ts
  • You walked through it on a clean account once; ended up at /today with a usable preference row

12 · Risk register

The specific worries you named, each with a mitigation that is the responsibility of a phase above.

Confusing nav
Mitigation: Phase 4. One Settings hub. Four items in primary nav. Decision rule when in doubt: if a setting could plausibly belong in two places, it lives in Settings only, and any contextual entry points are links into Settings — never duplicates.
Onboarding maze
Mitigation: Phase 6. Four cards, fourth optional. Everything else has a default and is editable in Settings. The onboarding's job is to get the user to the first usable day, not to interview them.
Account amnesia
Mitigation: Phase 5. One screen, six actions. The hard one — delete-account — gets written first and tested against your real account, because the schema's cascade behaviour is the actual risk, not the UI.
Stateless on paper, leaky in fact
Mitigation: Phase 5 tiers + the retention test. Without the test, the rule is decorative. Write the test even if you have to ship the cron job stubbed.
Static beauty, broken wiring
Mitigation: Phase 3's "real-data smoke pass" — every v2 screen is loaded against a real Supabase plan and screenshotted into docs/parity/AFTER/ before it's considered done. Eyeball for undefined, NaN, empty strings, "—".
Old modules drift back in
Mitigation: Phase 0's kill list lives in the repo. Phase 8 deletions are scheduled, not optional. Until then, the old modules are flag-gated off in nav so a stray import doesn't re-surface them.
Friday rush breaks production
Mitigation: Friday's flag flip is the only production change. Code deletions land the same day but the table drops wait until Monday week 2. If the weekend reveals an issue, you can flip the flag back and the old code is still there.

Delete-account endpoint sketch

// src/pages/api/auth/delete-account.ts
import type { APIRoute } from 'astro';
import { createServerAuth } from '@/lib/auth/simple-multi-user';

export const POST: APIRoute = async ({ cookies }) => {
  const serverAuth = createServerAuth(cookies);
  const user = await serverAuth.requireAuth();
  // RLS-scoped client — cascades handle most of this, but be explicit
  await serverAuth.supabase.from('daily_plans').delete().eq('user_id', user.id);
  await serverAuth.supabase.from('manual_anchors').delete().eq('user_id', user.id);
  await serverAuth.supabase.from('location_travel_profiles').delete().eq('user_id', user.id);
  await serverAuth.supabase.from('calendar_sources').delete().eq('user_id', user.id);
  await serverAuth.supabase.from('user_preferences').delete().eq('user_id', user.id);
  await serverAuth.supabase.from('profiles').delete().eq('id', user.id);
  // finally, the auth user — requires admin client
  const { error } = await serverAuth.adminClient.auth.admin.deleteUser(user.id);
  if (error) return new Response(error.message, { status: 500 });
  return new Response(null, { status: 204 });
};
